# 2026-09-24 复发调查：更新后长时间无窗口、受保护安装包文件与安装卷对照

> 这是一次个人机器的排障记录，不是 ChatGPT/Codex Windows 应用的通用诊断或官方修复说明。本文只讨论“启动后有进程，但窗口迟迟不出现”。文件路径中的用户目录已抽象化；未上传原始日志、账户数据或完整取证目录。

## 结论先说

这次故障发生在应用更新后、准备新版本 `cua_node` 运行时的阶段。更新前的运行时不能直接供新版本使用。重装前，应用包实际位于非系统应用卷 `E:\WindowsApps`，其运行时源文件标记为 `Application Protected`；普通 Windows 文件复制在本机报 `ERROR_ENCRYPTION_FAILED (6000)`。当前版本虽然会在失败后逐文件改用读取和写入内容，但这个同步处理过程耗时较长，窗口在取证时仍未出现。

**本次记录没有证明应用会永久卡死。** 取证时距离启动约 76 秒；随后我运行了手动修复脚本，因而无法观察如果不干预，原启动会在何时自行完成。隔离实验显示，相同类型的暂存目录在复制仍进行时也可能缺少必要文件。

后来我把 Microsoft Store 安装位置改为系统盘并重装。新包实际位于 C 盘，所检文件不再带加密标记，新版运行时也完整生成。这个本机迁移前后对照支持“安装卷上的受保护文件与复制方式冲突”是此次复发的关键条件；由于重装也换了应用版本，而且尚未观察下一次自动更新，**不能据此承诺以后绝不复发**。同一[公开问题讨论](https://github.com/openai/codex/issues/25220)既有迁回 C 盘后恢复的案例，也有迁回 C 盘后源文件仍受保护的反例。

## 时间线和直接证据

| 北京时间 | 观察 |
| --- | --- |
| 13:22 | Windows 将 `OpenAI.Codex` 包从 `26.917.6896.0` 更新到 `26.917.8451.0`，注册结果为 `0x0`。 |
| 13:26 | 新版应用进程启动；日志显示选择 bundled runtime 并进入启动流程。 |
| 13:26–13:27 | 生成 `.staging-7f75cff94511d5f8-*`；取证时暂存目录有 `bin/node.exe`，但缺少 `manifest.json` 和 `bin/node_repl.exe`。旧运行时目录仍存在。 |
| 13:27:21 之后 | 运行了既有修复脚本；事后新运行时正式目录出现。 |
| 当日下午 | 改用系统盘安装并重装，得到新版 `26.917.9434.0`；包文件状态和运行时部署结果见下文。 |

原安装包表面路径是 `C:\Program Files\WindowsApps\OpenAI.Codex_26.917.8451.0_x64__2p2nqsd0c76g0`，但该目录是指向 `E:\WindowsApps\...` 的 junction。`Get-AppxDefaultVolume` 当时返回 `E:\WindowsApps`、`IsSystemVolume=False`。`cipher /c` 对包内 `cua_node/manifest.json` 显示 `E` 和 `Compatibility Level: Application Protected`；文件属性也包含 `Encrypted`。目标 `%LOCALAPPDATA%\OpenAI\Codex\runtimes\cua_node` 在 C 盘普通用户目录，已复制出的文件未加密。

对原包内同一个 manifest 做独立 Windows `CopyFileW` 测试，返回错误 **6000 / `ERROR_ENCRYPTION_FAILED`**；读取文件内容再写入普通目录成功，内容一致。微软说明普通文件复制会尝试在目标重建源文件的加密状态，无法完成时会报此错误；`xcopy /G` 允许创建解密后的目标文件。[Windows 错误码](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--6000-8199-) · [加密文件复制行为](https://learn.microsoft.com/en-us/windows/win32/fileio/handling-encrypted-files-and-directories) · [xcopy `/G`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/xcopy)

## 为什么会在更新后重现

对当时 `app.asar` 中部署逻辑的只读检查发现：应用按 `manifest.json`、`bin/node.exe`、`bin/node_repl.exe` 的内容计算版本化运行时 ID；正式目录不可用时，创建暂存目录，递归复制完整运行时，再完成目录切换。复制每个文件时先调用普通复制；遇到加密相关的 `6000` 或 `UNKNOWN/-4094`，回退到读取并写入文件内容。该递归过程在窗口出现前的初始化路径上同步进行。

按应用相同的三个文件哈希规则计算，故障包需要的 ID 为 `7f75cff94511d5f8`，与取证时的暂存目录吻合。旧运行时属于旧版本，手动补齐一次不能让未来的新版免于重新准备文件。

在**独立测试目录**的复现结果：

| 测试 | 结果 |
| --- | --- |
| 模拟当前应用的逐文件“普通复制失败→读写回退” | 到 70 秒约完成 618 个文件；180 秒上限时完成 1908/2283 个。已处理的 1908 个文件均先报 `UNKNOWN/-4094`，之后读写成功。测试按时间上限停止，不能推断其最终一定失败。 |
| 直接按字节复制完整运行时 | 2283 个文件、250,613,786 字节，约 10.75 秒完成；逐文件 SHA-256 检查无差异。 |

这些是隔离实验，不是原故障进程的精确耗时记录。它们说明在复制尚未完成时，暂存目录缺少 `manifest.json` 和 `node_repl.exe` 并不罕见。以前文章中笼统写作“部署失败”，对**本次**应更准确地表述为“加密错误导致逐文件回退，取证时部署仍未完成”；不能把本次机制自动套到 9 月 8、9 日的每次故障。

## 迁到 C 盘后的本机对照

我将商店默认应用卷设为系统盘，卸载并重装该应用，然后做了只读复核：

| 检查项 | 迁移前 | 迁移后 |
| --- | --- | --- |
| 默认 AppX 卷 | `E:\WindowsApps`，非系统卷 | `C:\Program Files\WindowsApps`，系统卷 |
| 应用包实际位置 | C 盘表面目录是指向 E 盘的 junction | 新包 `26.917.9434.0` 实际位于 C 盘；不是指向 E 盘的 junction |
| 包内 `cua_node/manifest.json` | `Archive, Encrypted`；`cipher /c` 为 `Application Protected` | 仅 `Archive`；`cipher /c` 为 `U`（未加密） |
| 运行时正式目录 | 故障取证时，新版仍在 staging | 重装后正式目录存在；源/目标均为 2283 个文件、250,613,742 字节，三个必要文件的 SHA-256 一致 |

迁移后针对新包进行一次额外普通复制探针时，当前执行器的自动审批拒绝启动该命令；因此这里**没有**声称新包的 `CopyFileW` 探针已实测成功。目标文件未加密和运行时完整部署，是已直接观察到的事实。未来一次应用自动更新仍是验证“长期不复发”的关键观察点。

## 处理办法与适用范围

1. **出现无窗口时先取证。** 对照同次启动的进程、日志、当前包版本及其新运行时暂存目录。只有确认属于此类运行时准备问题后，才考虑既有的 [`Fix-ChatGPT.bat`](../Fix-ChatGPT.bat) 和 [`Fix-ChatGPT.ps1`](../Fix-ChatGPT.ps1)。旧脚本按当次暂存目录找 ID，属于事后恢复，不是永久修复。
2. **手动 `xcopy /G` 是绕过复制兼容问题。** 每次更新可能需要新运行时，因此每版重复手工复制不是根治。曾制作“启动前自动复制”的本地试验启动器，但它本质上仍是 `xcopy`，没有作为长期解决方案发布。
3. **将商店应用装到系统盘是可验证的环境调整。** 本机迁移后源文件不再加密且运行时已就绪；公开报告存在不同结果，仍须以本机后续更新为准。不要直接修改 `WindowsApps` 的权限、签名文件或加密属性。
4. **应用侧的根治方向**是让运行时部署对可读但受 `Application Protected` 保护的文件使用允许解密目标的复制方式，或直接读写内容并避免每个文件先经历一次失败；同时避免长时间同步阻塞窗口并提供可见进度。

## 关于旧 E 盘 `WindowsApps` 文件夹

ChatGPT 新包搬到 C 盘后，E 盘顶层没有旧 `OpenAI.Codex_*` 目录。但 `E:\WindowsApps` **不是可删除的 ChatGPT 备份**：当前用户的应用登记仍把 VS Code、三个 WPS 扩展和一个系统分享组件列在 E 盘应用卷，C 盘这些同名包目录反而是指向 E 盘的 junction。即使曾手动复制过目录，也不能把当前 Windows 正在使用的 E 盘应用卷当作闲置副本直接删除。微软的 [`Remove-AppxVolume` 文档](https://learn.microsoft.com/en-us/powershell/module/appx/remove-appxvolume?view=windowsserver2025-ps)要求先确保所有用户在该卷上都没有暂存应用。
